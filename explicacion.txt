### Explicación del Código y Tecnologías

Hola! Aquí tienes una explicación del proyecto, pensada para alguien que sabe programar pero no está familiarizado con el desarrollo backend (servidores) o servicios en la nube. El objetivo es darte una idea clara de qué hace cada parte y por qué se eligió.

--- 

### 1. ¿Qué Construimos? (El Panorama General)

Imagina que tienes una empresa que participa en licitaciones públicas. Cada licitación tiene un montón de documentos (PDFs). Revisarlos a mano es lento y propenso a errores. 

Este proyecto es una **aplicación web mínima** que automatiza ese proceso:

1.  **Subes los PDFs**: Un usuario sube los documentos de una licitación (llamada `case_id`).
2.  **La IA los Analiza**: Un "trabajador" (worker) en la nube toma esos PDFs, extrae el texto y usa un modelo de Inteligencia Artificial (como Gemini de Google) para sacar datos clave (quién es el contratista, el monto, las fechas, etc.).
3.  **Genera Resultados**: El sistema guarda esta información estructurada (en formato JSON), identifica posibles riesgos (ej. "no hay garantía"), compara las ofertas si subiste varias, y genera un reporte simple en PDF y una fila en un Google Sheet.
4.  **Visualizas en un Dashboard**: Usando Looker Studio (una herramienta gratuita de Google), puedes conectar ese Google Sheet para crear un tablero interactivo y ver los resultados de forma gráfica.

La clave es que todo esto es **"serverless"** (sin servidor), lo que significa que no tienes que preocuparte por administrar servidores. Pagas solo por lo que usas, lo cual es ideal para empezar.

--- 

### 2. Tecnologías Utilizadas (Las Piezas del Lego)

**a) FastAPI (Para la API)**

*   **¿Qué es?**: Es un framework de Python para construir APIs (Interfaces de Programación de Aplicaciones). Una API es como el mesero de un restaurante: el cliente (tu navegador o una aplicación) le hace un pedido (ej. "quiero subir este archivo") y la API se encarga de que el backend (la cocina) lo procese y devuelva una respuesta.
*   **¿Por qué se usa?**: Es muy rápido, moderno, fácil de aprender y documenta automáticamente tus "endpoints" (las URLs que tu API expone, como `/upload-init` o `/result/{case_id}`). Es ideal para crear servicios web eficientes con Python.

**b) Google Cloud Run (Para ejecutar el código)**

*   **¿Qué es?**: Es un servicio de Google Cloud que ejecuta tu código sin que tengas que pensar en servidores. Simplemente le das tu código (empaquetado en un "contenedor Docker") y Google se encarga de ejecutarlo, escalarlo si recibe muchas peticiones, y apagarlo si no se usa.
*   **Se usa de dos formas aquí:**
    1.  **Cloud Run Service (para la API)**: Es un servicio que está siempre "escuchando" peticiones. Nuestra API con FastAPI corre aquí, esperando a que un usuario quiera subir un archivo o ver un resultado.
    2.  **Cloud Run Job (para el Worker)**: Es para tareas que se ejecutan, hacen su trabajo y terminan. El análisis pesado de los PDFs se hace aquí. La API le dice "¡Oye, analiza estos documentos!" y el Job se inicia, procesa todo (puede tardar minutos) y se apaga solo. Esto es más barato que tener un servicio potente corriendo todo el tiempo.

**c) Google Cloud Storage (GCS) (Para guardar archivos)**

*   **¿Qué es?**: Es el disco duro en la nube de Google. Un lugar para almacenar cualquier tipo de archivo (PDFs, JSONs, imágenes, etc.). Es muy barato, seguro y escalable.
*   **¿Cómo se usa?**: 
    *   `raw/`: Guardamos los PDFs originales que sube el usuario.
    *   `work/`: Guardamos archivos intermedios, como el texto extraído de los PDFs.
    *   `results/`: Guardamos los JSON con los datos extraídos y la comparación.
    *   `reports/`: Guardamos el reporte en PDF que se genera.

**d) Google Sheets API (La "Base de Datos" simple)**

*   **¿Qué es?**: Es la API que permite a un programa leer y escribir en hojas de cálculo de Google Sheets, como si fuera un usuario.
*   **¿Por qué se usa?**: Para este proyecto, no necesitamos una base de datos compleja como SQL. Un Google Sheet es suficiente para guardar un resumen de los KPIs (Key Performance Indicators, como el monto o el nivel de riesgo) de cada licitación. Es una forma rápida y visual de tener una base de datos simple.

**e) Looker Studio (El Dashboard)**

*   **¿Qué es?**: Una herramienta gratuita de Google para crear reportes y dashboards interactivos a partir de diferentes fuentes de datos.
*   **¿Cómo se usa?**: Lo conectas a nuestro Google Sheet y en minutos puedes crear gráficos de barras, tablas y filtros para visualizar los datos de las licitaciones de forma amigable.

**f) Vertex AI (Gemini) (El Cerebro de IA)**

*   **¿Qué es?**: La plataforma de Google para usar modelos de Machine Learning e IA. Gemini es uno de sus modelos más potentes, similar a ChatGPT.
*   **¿Cómo se usa?**: Le enviamos el texto extraído del PDF junto con un "prompt" (instrucciones) muy específico que le dice: "Extrae estos campos y devuélvemelos en formato JSON". El worker se encarga de hacer esta llamada.

**g) Docker (El "Contenedor" o "Tupper" para el código)**

*   **¿Qué es?**: Es una herramienta para empaquetar tu aplicación y todas sus dependencias (librerías, configuraciones, etc.) en una unidad aislada y portable llamada "contenedor".
*   **¿Por qué se usa?**: Imagina que tu código funciona en tu laptop pero no en la de un amigo porque le falta una librería. Docker resuelve esto. Creas una "imagen" que es una receta de tu entorno. Cloud Run usa esta imagen para ejecutar tu código, asegurando que siempre funcione igual en cualquier lugar. Tenemos dos `Dockerfile`, uno para la API y otro para el Worker, que son las recetas para construir sus respectivos contenedores.

### 3. Estructura del Código (El Mapa del Proyecto)

*   `api/`: Contiene todo el código del servidor web (la API con FastAPI).
    *   `main.py`: El archivo principal que define los endpoints (`/upload-init`, `/process`, etc.).
    *   `schemas.py`: Define la estructura de los datos que la API espera recibir y enviar (los "contratos").
    *   `gcs.py`: Lógica para interactuar con Google Cloud Storage (ej. crear URLs firmadas para que el cliente suba archivos de forma segura).
    *   `config.py`: Carga las variables de entorno (como el nombre del bucket o el ID del proyecto).
    *   `Dockerfile`: La receta para construir la imagen Docker de la API.
    *   `requirements.txt`: La lista de librerías de Python que necesita la API.

*   `worker/`: Contiene todo el código del "trabajador" que analiza los documentos.
    *   `run.py`: El punto de entrada del job. Orquesta todo el proceso.
    *   `pipelines/`: Cada archivo aquí es un paso del proceso (WF-01 a WF-05). Esto mantiene el código ordenado.
    *   `utils/`: Funciones de ayuda que se usan en varias partes del worker (ej. para extraer texto de PDF, para hablar con la API de Google Sheets, etc.).
    *   `prompts/`: Guarda el texto del prompt que le damos al modelo de IA.
    *   `Dockerfile`: La receta para construir la imagen Docker del Worker.
    *   `requirements.txt`: Las librerías que necesita el Worker.

*   `infra/`: Contiene archivos de configuración de infraestructura (opcionales).
    *   `cloudrun_api.yaml`, `cloudrun_job.yaml`: Describen la configuración de los servicios de Cloud Run en formato YAML. Es una forma de documentar la configuración.

*   `tests/`: Pruebas automáticas para asegurar que el código funciona como se espera.

*   **Archivos en la raíz:**
    *   `.env.example`: Una plantilla de las variables de configuración que necesitas.
    *   `Makefile`: Un archivo con atajos de comandos para tareas comunes (como `make install` o `make run-api`).
    *   `README.md`: La documentación principal del proyecto.
    *   `instructions.txt`: El archivo que estás leyendo ahora.

Espero que esta explicación te sea de gran ayuda para entender el proyecto. ¡Es un stack tecnológico muy moderno y potente para construir aplicaciones en la nube de forma rápida y eficiente!
